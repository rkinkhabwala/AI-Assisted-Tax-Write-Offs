# WriteOff Assistant: build plan

Source of truth: [spec.md](spec.md). Phases follow spec section 10. A phase is done only
when its tests pass and `make lint` is clean, with no TODO stubs or `pass` placeholders.
Each STOP waits for approval. To resume: "Read PLAN.md and continue from the first
unchecked item."

## Decisions (defaults adopted in phase 1; accepted when phase 2 was approved)

| # | Question | Default adopted | Changes if overridden |
|---|---|---|---|
| D1 | Embedder: the spec names `voyage-3`, which Voyage now lists as legacy | `voyage-4` (1024-d). A/B against `voyage-law-2` (also 1024-d) in phase 4 | Nothing if the replacement is 1024-d; otherwise a new migration |
| D2 | Reranker | Voyage `rerank-2.5` (`rerank-3` is still in preview) | Config value only |
| D3 | UI: Streamlit or React | Streamlit | Phase 9 scope; React adds a JS build and a second container |
| D4 | "Never split a table" conflicts with "no chunk over 1,200 tokens" | The **parent** chunk holds the whole table, uncapped, and the agent reads that. Oversized tables get **child** chunks by row group with the header row repeated, each ≤1,200 | Chunker design (phase 2) |
| D5 | Lexical search: Postgres FTS or true BM25 | Built-in FTS (`tsvector` + `ts_rank_cd`). Citation path indexed with the `simple` config so "280a" and "8829" match verbatim | BM25 needs ParadeDB `pg_search`: a different Postgres image and a new migration |
| D6 | Entity-type applicability | `entity_types text[]` per chunk, empty = applies to all. Tagged by rule at ingestion (e.g. Form 1120-S → `s_corp`). Filter: empty OR contains | Ingestion tagging (phase 2) and the filter SQL (phase 3) |
| D7 | Tax-year versioning of statutes, which have no annual editions | Snapshot the IRC and regs once per supported year, so every chunk has one `tax_year` and one filter works everywhere | Storage roughly doubles for statutes; an alternative is effective-date ranges |
| D8 | IRC source | uscode.house.gov section pages. Their `substructure-location_c_1_A` anchors give the exact hierarchy, so the multi-MB whole-title USLM XML isn't needed. Cornell isn't used | Parser in phase 2 |
| D9 | Models | Agent `claude-sonnet-5`; per-chunk context summaries `claude-haiku-4-5-20251001` (runs once per chunk) | Cost and latency; config only |
| D10 | Supported tax years | 2025 and 2026 | Parameter files and ingestion scope |

Also noted for phase 6: the Agent SDK drives a bundled Claude Code CLI subprocess, one per
client, so the API must manage client lifetimes per session. The current `ClaudeAgentOptions`
has a separate `tools` field. Restricting `allowed_tools` alone may not disable
built-in tools, so check against the SDK docs at that point.

Decisions for the user / carried forward:
- **Larger chunks (500–1,100 tokens) scored best** of the chunking variants (vs same-settings `noctx`: MRR +4.8, nDCG +2.4, R@10 +0.5). Switching production means re-summarizing about 5.9k chunks (roughly $10 Claude) and coarser citations. Awaiting a decision.

## Phase 7: grounding verifier ✅
- [x] Evidence capture (`agent/evidence.py`): the tool runtime records every retrieved passage (all texts per citation, since grouped parents can share one), parameter and calculator result per request
- [x] Deterministic checks (`agent/verifier.py`): every `[citation]` must resolve to retrieved evidence (sub-provisions of retrieved sections, broader cites, and heading paths with skipped intermediate headings resolve); every $ / % / cents figure must appear in the evidence or the user's question
- [x] Judge: a separate Claude call (`verifier_model`, Sonnet 5, thinking off) through `messages.parse` with structured output. It sees only the question, the draft and the *cited* evidence. It labels claims SUPPORTED / PARTIALLY_SUPPORTED / UNSUPPORTED and returns targeted replacements rather than a rewritten answer
- [x] Loop: edits applied → round 2 re-judges only the edited sentences (with deterministic checks on the full text) → if still failing, unsupported lines, untraced figures and unknown citations are stripped. Anything narrowed or dropped is disclosed in a note before the disclaimer. A judge outage returns the draft with an "unverified" note
- [x] Results stored per request (migration 0003: status, rounds, claim counts, unknown citations, untraced figures, verifier tokens) and shown in the CLI trace
- [x] Tests: 303 total (tag resolution incl. abbreviations, figure tracing, cited-evidence selection, every loop outcome with a scripted judge, the structured-output request against a mocked API, evidence capture, harness integration, persistence)

Known gaps:
- No per-user accounts or rate limiting beyond one shared bearer token.
- The concurrency cap is per process.
- The store opens a connection per call (no pool). Fine at this scale.
- The chat endpoint doesn't screen pasted CSV text the way uploads are screened; the agent treats it as data and the eval shows 5/5 resisted. Uploads are the refused path.
- Streamlit keeps chat history in the browser session only; the API session persists its facts and the SDK conversation.
